# Agent Instructions (에이전트 행동 수칙)

## 0. 작업 시작 전 인수인계 확인
- **HANDOFF.md 먼저 읽기**: 작업을 시작하기 전에 프로젝트 루트의 `HANDOFF.md`를 읽고, 현재 상태와 다음 할 일을 사용자에게 짧게 확인한 뒤 시작하십시오.
- **작업 후 갱신**: 작업 주제가 끝나거나 바뀌면 `HANDOFF.md`를 덮어써 갱신하고 `chore(handoff): <한 줄 요약>`으로 커밋하십시오. 비밀번호·API 키·접속 주소·토큰은 적지 않습니다.

## 0-1. 개발 DB 터널
- **DB 작업 전 터널 확인**: 개발 DB는 SSH 터널(로컬 13306 포트)로만 접속됩니다. DB를 쓰는 작업(dev 서버, prisma, tsx 스크립트) 전에 `npx prisma migrate status`로 접속을 확인하고, 안 되면 `pnpm db:tunnel`을 백그라운드로 실행하십시오.
- **이미 떠 있으면 그대로 사용**: `pnpm db:tunnel`이 `Address already in use`로 바로 끝나면 이전 세션의 터널이 살아 있는 것이므로 새로 띄우지 말고 그대로 쓰십시오. 백그라운드 작업을 중지해도 ssh 프로세스가 남을 수 있습니다.
- **새 PC 준비(사람)**: `~/.ssh/config`에 `Host zinsight-db` 항목(HostName·User·Port·IdentityFile·LocalForward 13306)과 키 파일이 있어야 합니다. 접속 정보는 저장소에 적지 않습니다.

## 0-2. Next.js 버전
- **문서 먼저 확인**: 이 프로젝트의 Next.js(16.x)는 학습 데이터와 API·규칙·파일 구조가 다를 수 있습니다. 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 해당 가이드를 읽고 지원 중단 안내를 따르십시오.
- 루트 `AGENTS.md`는 `next.config.js`의 `agentRules: false`로 만들지 않습니다. 에이전트 규칙은 이 파일에만 적습니다.

## 0-3. 비밀 값 취급
- **출력 금지**: 비밀번호·API 키·토큰·DB 접속 주소 같은 비밀 값을 화면 출력·`echo`·로그·커밋 메시지·문서에 쓰지 마십시오. `.env` 계열 파일과 서비스 계정 키 파일은 읽지 않습니다(`.claude/settings.json`에서 차단). 키 이름이 필요하면 `.env.example`을 보십시오.
- **DB 접속은 환경변수 참조만**: 접속 정보를 명령어나 코드에 직접 적지 말고 `DATABASE_URL` 등 환경변수를 참조하십시오.
- **예시는 자리표시자**: 명령어 예시에는 실제 값 대신 `<PASSWORD>`, `<HOST>`, `<TOKEN>` 같은 자리표시자를 쓰십시오. 예) `mariadb -u <USER> -p<PASSWORD> <DB_NAME>`

## 1. 빌드 및 데이터베이스 마이그레이션 규칙
- **필요 시에만 빌드 실행**: 단순한 UI 마크업 변경, CSS 클래스 조정, 텍스트 수정과 같이 데이터베이스 스키마 구조 변경이나 엄격한 TypeScript 타입 인터페이스가 바뀌지 않는 사소한 마크업 작업 시에는 매번 전체 프로덕션 빌드(`pnpm build`)를 돌리지 마십시오.
- **마이그레이션 최소화**: 실서버 데이터베이스 마이그레이션 및 동기화는 데이터베이스 스키마 변경(`schema.prisma` 수정 등)이 있을 때만 명시적 근거 하에 선별적으로 구동하십시오.
- **개발 환경 위주의 검증**: 빌드나 작동 검증이 필요한 경우 가능하면 로컬/개발 환경 기준의 검증을 우선하고, 실서버용 변수가 들어간 빌드는 배포 전 마지막 완성 시점에 단 한 번 검증하거나 생략하십시오.

## 2. 데이터베이스 직접 수정 규칙
- **단순 삽입은 허용**: 기능 검증용 테스트 데이터·초기 데이터 등록처럼 새 행을 추가하는 단순 INSERT(앱 화면·API를 통한 입력 포함)는 에이전트가 직접 실행할 수 있습니다.
  - 개발 DB는 바로 실행하고, 운영 DB는 실행 전에 대상과 내용을 알리고 승인을 받으십시오.
  - 검증용으로 넣은 데이터는 확인이 끝나면 에이전트가 직접 삭제합니다 (자신이 넣은 행만, id로 지정).
- **수정·삭제는 보고만**: 기존 데이터를 바꾸거나 지우는 UPDATE / DELETE는 실행하지 말고 필요한 SQL을 정리해 사용자에게 보고하십시오. 사용자가 직접 실행합니다.
- **스키마 변경은 별도**: `schema.prisma` 수정 후 마이그레이션(`prisma migrate`)은 위 1번 규칙에 따라 스키마 변경이 있을 때만 별도 판단하십시오.

## 3. 마이그레이션 적용 절차
- **운영 DB는 배포가 적용**: Vercel 빌드 명령이 `npx prisma migrate deploy && next build`이므로, 운영 DB(`.env`의 주석 처리된 DATABASE_URL)에는 배포 시 미적용 마이그레이션이 자동 적용됩니다. 마이그레이션 SQL을 운영 DB에 수동 실행하지 마십시오. 수동 실행 후 배포하면 `P3018`(중복 컬럼 등)로 배포가 막힙니다.
- **에이전트가 실행 가능한 명령**: 스키마 변경에 따른 `prisma migrate deploy`(개발 DB 적용)와 `prisma migrate resolve`(이력 복구)는 에이전트가 직접 실행할 수 있습니다. 대상 DB는 명령 실행 시 `DATABASE_URL`을 지정해 선택합니다.
- **운영 DB는 매번 확인**: 운영 DB를 대상으로 하는 마이그레이션 명령은 실행 전에 대상과 명령을 사용자에게 알리고 승인을 받은 뒤 실행하십시오.
- **데이터 변경은 2번 규칙 적용**: 마이그레이션이 아닌 데이터 변경은 2번 규칙대로 단순 삽입만 직접 실행하고, 수정·삭제는 SQL만 정리해 보고합니다.

- **한글로만 작성**: 모든 Git 커밋 메시지는 반드시 한글로만 작성하십시오.
